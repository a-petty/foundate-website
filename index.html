01 / COMPANY-OWNED AI

Built · pilot next

An AI Chief of Staff.
Owned by the
company.

Company systems & daily operations

  • Morning briefs
  • Meeting prep
  • Follow-up drafts
  • Weekly reviews

The challenge

Priorities, meeting context, and commitments are scattered across inboxes, calendars, and notes. Keeping up depends on people pulling it all together.

What we built

A company-owned AI Chief of Staff that brings that context into a useful daily rhythm: what needs attention, what to know before a meeting, and what needs to happen afterward. Built into the tools people already use, with company-managed installation and access as the foundation.

Inside the Chief of Staff system

Built into the workflow

  • Email, calendar, meeting notes, and a personal commitment register feed the four outputs.
  • Checks require recommendations to cite supplied evidence and flag inputs the system could not read.
  • Follow-ups remain drafts and proposed commitments for the person to review.
  • It runs as each person inside the company’s own Google account and never sends mail on anyone’s behalf.

How it was checked

More than 70 automated tests run all four workflows on synthetic people. Any recommendation that cites nothing from its inputs is removed, dates are written by code rather than the model, and a static check confirms it can only send mail to its own user. A staff pilot in the company’s own Google account is next.

02 / REPORTING AUTOMATION

Built · pilot next

Manual reports.
Rebuilt as
automated workflows.

A centralized reporting automation hub

  1. Bring the report
  2. Rebuild its rules
  3. Check the results
  4. Review & release

The challenge

Teams repeat the same data pulls, spreadsheet updates, and checks every reporting cycle. The process often lives in a workbook and in the head of the person who maintains it.

What we built

A centralized hub that takes an existing manual report, captures its rules, and uses AI to build an automated version. The workflow brings report requests, validation, and release review together, with people deciding whether the result is ready to use.

Inside the reporting automation hub

How a report moves through the system

  • Start with the report, its source data, business rules, and past examples.
  • The AI builder writes the automation using synthetic practice data.
  • Separate checks compare the result with a known-correct answer key and confirm the generated automation follows its operating rules.
  • Before a report is released, it is compared with historical versions, run for two live cycles alongside the manual process, and approved and published as separate human steps.

How it was checked

On practice data, the first AI-built report reproduced all twelve months exactly when run on Google, with no differences from the known-correct result. No real report has gone through it yet; the first one is next.

03 / INCENTIVE COMPENSATION

From spreadsheet rules
to a reviewable
bonus workflow.

Finance & people operations

The challenge

Quarterly bonus calculations brought together performance metrics, eligibility, targets, and manual adjustments across a complex workbook.

What we built

A calculation engine and review interface that put the rules in one place, expose missing inputs, and make exceptions explicit.

Inside the compensation implementation

Built into the workflow

  • Workbook and warehouse inputs connected to the same calculation logic.
  • Target setting, exceptions, substitutions, and approvals available through the review interface.
  • Data-quality checks that block publication when required inputs are missing or ambiguous.

How it was checked

Historical payout workbooks were compared with the engine and a separate, independent calculation. The documented review accounted for discrepancies and checked that incomplete results stayed blocked.

04 / MONTHLY REPORTING

A repeatable path
from source data
to variance reports.

Asset management

The challenge

Monthly reporting required financial actuals, operating measures, budget comparisons, and commentary to come together in a hand-maintained spreadsheet.

What we built

A reporting application with warehouse-fed actuals, budget inputs, variance flags, and commentary. Source history and saved report versions help explain how a number changed.

Inside the reporting implementation

Built into the workflow

  • Entity and period selection, current-month and year-to-date comparisons, and variance review.
  • One calculation engine shared by the application and its reconciliation checks.
  • Versioned source values and locked published-report snapshots for historical traceability.

How it was checked

Report calculations were reconciled against reference workbooks, with differences classified and documented. The running application was reviewed with warehouse-fed financial and operating data.

05 / ANNUAL PLANNING

A budget process
built around review
and approval.

Finance & asset management

The challenge

A detailed annual budget model needed to become a repeatable process for reviewing assumptions, comparing scenarios, and carrying approved decisions into the final calculation.

What we built

A planning application with editable assumptions, scenario comparisons, separate approval, and locked budget versions. New budget cycles can run without the original workbook.

Inside the planning implementation

Built into the workflow

  • Assumptions and plan inputs move together through drafting, review, and approval.
  • Approved values are locked and used by the final budget calculation.
  • Separate client and annual cycles preserve their own data, assumptions, and review state.

How it was checked

Documented reference validation reproduced a prior-year model through the workbook-free calculation path. A separate test exercised the full draft-to-approved-to-final sequence. Next-year budget cycles were prepared for team review.

The common thread: understand the process, make the rules explicit, and build in a way to check the result.
